## 为什么做这个项目

现有的 AI 产品几乎都长一个样：左边一列历史对话，中间一片聊天记录，底下一条输入框。Agent 到底在干什么、干到哪了、有没有做到你要求的事，全都塞在一条条消息里。

这个项目的出发点是一句话：

> **少做架构，多做实验。少做基础设施，多做界面。少考虑统一，多考虑发散。**

所以这里没有组件库，没有设计系统，没有 SDK，也没有 Agent 运行时。十个实验各自是一个独立的小界面，有自己的颜色、字体和排版，**互相不 import，也不为了复用而抽象**。唯一不变的问题是那一句：

> **Agent 干活的过程，用户看得懂吗？**

项目分两个阶段。001 到 006 问的是「Agent 的工作过程还能怎么表达」；从 007 开始问的是「如果这是一个真正给人使用的 Agent UI，它还能长什么样」。

## 快速开始

前置要求：Node.js 20 以上、pnpm。

实测环境是 Node.js v24.21.0 与 pnpm 11.7.0。

```sh
git clone https://github.com/ChenChen913/agent-ui-lab.git
cd agent-ui-lab
pnpm install
pnpm dev
```

打开终端里打印的地址（默认 http://localhost:5173 ），先看到的是总页面。

## 十五个实验

| 编号 | 名称 | 它在回答什么 |
|---|---|---|
| 001 | The Bench | Agent 干活的时候，界面除了转圈还能是什么样？ |
| 002 | One Line | 如果整个界面只允许存在一条线，Agent 还能怎么工作？ |
| 003 | Terminal | 终端本身很粗糙，能不能把它设计成一个高级的 Agent Interface？ |
| 004 | Chronicle | 如果不用传统聊天记录，而是用时间轴表达 Agent 的工作过程，会怎么样？ |
| 005 | Desktop | 如果 Agent 不是一个网页，而是一个活在桌面上的存在，会怎么样？ |
| 006 | Spatial | 如果 Agent 的状态不是用列表表达，而是用空间关系表达，会怎么样？ |
| 007 | The Brief | 如果界面的主角是「这份委托」，而不是聊天记录，会怎么样？ |
| 008 | Baseline | 用户登录之后第一眼看到的那一层，应该长什么样？ |
| 009 | Workbench | 如果产出不是最后一条消息，而是一个放在旁边的产物呢？ |
| 010 | Home | 如果首页本身就是这个产品，输入框悬在正中，会怎么样？ |
| 011 | Bubble | 如果 Agent 就长成你最熟悉的那个聊天软件的样子呢？ |
| 012 | The Plan | Agent 已经开干了，你才发现它理解错了，除了打断重来还能怎么办？ |
| 013 | Weight | 同一块界面，面对一句话和二十个项目，应该给出同样分量的过程吗？ |
| 014 | Settle | 过程和结果，是两个东西，还是同一个东西的两个阶段？ |
| 015 | Return | 用户离开 20 分钟再回来，界面上应该是什么？ |

008 到 015 默认停在用户刚打开时的空状态，点右上角的播放键才会开始演示。

每个实验目录里有一份 `NOTES.md`，记录「我在探索什么 / 发现了什么 / 下次想试什么」。

## 用法

总页面在 `/`，每个实验有自己的路由：

```
/            总页面，十个实验的入口
/001/a       001 的三套皮肤分别是 /001/a、/001/b、/001/c
/002 … /015  其余实验
```

每个实验页面右上角有一条控制栏：返回总页面、切上一个 / 下一个实验、切换白天黑夜、播放 / 暂停、重播、调速（0.5 倍 / 1 倍 / 2 倍）。

## 配置

**这个项目没有任何环境变量，也不需要任何密钥。**

命令：`Select-String -Path 'src\**\*.ts','src\**\*.tsx' -Pattern 'import\.meta\.env|process\.env'` → 命中 0 条。

所有数据都是写死在 `src/experiments/*/scenario.ts` 里的 Mock 数据。

## 一个实验是怎么做出来的

每个实验都走同一条路，顺序不能换：

1. **Concept**：先确定这个实验要回答的**一个问题**。写不出这一个问题，就不动手
2. **Interaction**：这个观点推出哪些交互？哪些是这个观点独有的？
3. **Visual Design**：视觉语言从观点推出来，不从别的实验继承
4. **Implementation**：一个目录写完，包含完整的界面、Mock 数据、状态变化、加载 / 完成 / 出错状态

每个实验都必须能真的点。不能只有一张图，也不能只有一个动画。

动画的实现方式在 002 之后统一成一种：**逐帧循环只写 CSS 变量和 DOM 样式，React 只在离散的节拍上重新渲染**。一个几十秒的演示通常只有几十次重渲染。

## 常见问题

**Q：为什么每个实验都自己写一套样式，不复用？**

A：复用会让十个实验慢慢长成同一个样子，那样就失去了比较的意义。`shared/` 目录只在同一个东西重复到第三次时才会出现，目前还没有。

**Q：能接真实的大模型吗？**

A：不能，也不打算接。这个项目研究的是界面，接上模型只会让注意力从排版和交互上移开。

**Q：为什么 008 到 010 打开是空白的？**

A：那不是空白，是用户登录后看到的空状态。点右上角的播放键可以看完整的演示流程。

## 已知限制

- 所有数据都是 Mock，没有真实的大模型调用，没有后端、数据库和登录
- 只有桌面端做了完整设计，移动端只做到「不崩」
- 项目没有配置测试框架，也没有 CI
- 003 的终端只实现了演示需要的少数命令（`clear`、Ctrl-C 等）
- 007 的条款不能就地编辑，只能通过回答来改写
