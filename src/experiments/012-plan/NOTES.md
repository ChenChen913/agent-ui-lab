# 012 · The Plan —— 设计笔记

> **这个实验在回答什么**
> Agent 已经开干了，你才发现它理解错了。除了「打断重来」，还能怎么办？

## 我在探索什么

这是第一条把两条主线接起来的实验。

- 001 到 006 研究的是**过程怎么显示**
- 007 到 011 研究的是**入口长什么样**
- 012 问的是：**过程能不能被用户当场改**

007 的整个前提是「开工前把话说清楚，之后就不会错」。012 直接检验这个前提：
**说到一半才发现说错了，才是常态。**

## 核心观点

> **计划本身就是界面，而且它是活的。**

不是「展示一个计划」，是「一个你可以当场改的计划」。
所以这里没有聊天记录、没有侧边栏、没有产物面板 —— 只有一张路线图。

## 最要紧的一点：涟漪是算出来的，不是演的

每一步声明自己依赖哪几步（`deps`）。改任何一步，就沿着 `deps` 往下做传递闭包，
算出来的就是要作废的步骤。

| 步骤 | 依赖 | 改 ② 之后 |
|---|---|---|
| ① 确定比较维度 | 无 | **不受影响** |
| ② 搜索并筛选候选 | 无 | 被改的那一步 |
| ③ 逐个收集信息 | ② | 将重做 |
| ④ 横向对比 | ①、③ | 将重做（经由 ③） |
| ⑤ 生成报告 | ④ | 将重做（经由 ④） |

**依赖关系直接印在每一步下面**（「依赖 2」「依赖 1、3」）。
这一点是刻意的：重排最容易变成「看起来很智能的假动作」，
用户看不出**为什么**要重排这几步，它就只是动画。
把依赖写出来，重排就变成了**可验证**的。

## 第二个关键：还没按回车，涟漪就显示了

编辑框打开、你开始打字的那一刻，下游的步骤就已经标成琥珀了，
底部同时给出「③④⑤ 会重做 · ①② 不受影响」。

**你是在看到后果之后才决定要不要改的**，而不是改完才发现搞砸了。

## 视觉

一条竖向轨道串起所有步骤。三种颜色都有功能含义，没有一种是装饰：

| 颜色 | 含义 |
|---|---|
| 靛蓝 `#2f4bb8` | 正在执行 / 正在编辑 |
| 墨绿 `#2f7d5c` | 已完成 |
| **琥珀 `#b8791a`** | **将重做（涟漪）** |

轨道本身也会变色：① 到 ② 之间是绿的，② 往下是琥珀的。
**作废的范围在轨道上是一条能看见的线。**

## 可以真的操作的五件事

| 操作 | 会发生什么 |
|---|---|
| **点任何一步的标题** | 就地改字；打字过程中下游实时标琥珀；回车应用，Esc 取消 |
| **删掉一步** | 那一步消失，依赖它的步骤重排 |
| **加一步** | 插到末尾 |
| **回答 Agent 的口径问题** | 点选项，当场重排 |
| **打断** | 正在跑的那一步变成「被你打断」 |

## 已知取舍

- 依赖关系是**写死的**，不是 Agent 推出来的。真实场景里这个推断本身就是难题
- 删掉一步之后，依赖它的步骤只是被标记，没有真的重新规划
- 「加一步」加进去的步骤不会被执行，只是挂在计划上
- 演示里只有一次重排（Agent 主动问口径那次）。用户自己改的路径要手动试

## 下次想试什么

- [ ] **部分复用**：作废的步骤里，已经收集到的信息能不能留一部分（现在是全丢）
