# B4 · Chronicle —— 设计笔记

> **这个实验在回答什么**
> 如果不使用传统聊天记录，而是用时间轴表达 Agent 的工作过程，会怎么样？

---

## 一、核心命题

### 聊天记录里，「时间」是丢失的

一条花了 0.2 秒的消息，和一条花了 40 秒的消息，**占一样的空间**。

于是你永远看不出：**Agent 把时间花在哪了。**

### 所以：时间不是序号，是长度

> **X 轴 = 真实毫秒。一根条有多长，它真的就花了多久。**

并行的三路调研 → **三条上下对齐的泳道**，谁慢一眼就看出来。

这一条推论就带来三个聊天记录做不到的东西：

1. **看得见耗时分布** —— Qdrant 那条"读 benchmark"明显比别人长一截，全片最慢的一步自己站出来了
2. **看得见并行** —— 三个候选是同时在查的，不是排队
3. **看得见空档** —— 15.8s–16.5s 有 0.7 秒什么都没跑。**聊天记录里，这段时间是不存在的**

## 三、关键机制：整张图是 t 的纯函数

没有"播放模式"和"回看模式"两套逻辑。只有：

```
每根条：  从 start 画到 min(t, end)
播放头：  在 t
详情面板：t 落在哪根条里，就显示哪根条
```

于是**拖动播放头 = 时间旅行**，自动就成立了。演示在播放时，条在实时生长；你一拖，整张图回到那一刻。

## 四、可以真的操作的五件事

| 操作 | 会发生什么 |
|---|---|
| **横向拖动** | 抓住图纸拖（平移视窗），自动脱离实时跟随 |
| **点击空白处** | 把播放头放到那一刻，**暂停实时** —— 和录像机一样 |
| **滚轮** | 以鼠标位置为锚点缩放（2.4s ~ 24s） |
| **悬停任意一根条** | 左栏泳道名跟着高亮，底部换成那一步的说明 |
| **点左侧泳道名** | 跳到那条泳道的开始 |

底部右侧会按情况出现「适应」和「回到实时」。

## 五、让「时间轴」成立的几个细节

| 细节 | 为什么 |
|---|---|
| **失败 = 斜纹条** | pgvector 的"核对版本"失败了 → 斜纹；紧接着一根**空心**的"重试"条。形状区分，不靠颜色 |
| **空档着色** | 15.8–16.5s 那段用极淡的底色标出来，底部文案点明「聊天记录里这段时间是不存在的」 |
| **并行组的方括号** | 左侧一个竖着的括号把三条泳道括起来，配一个竖排的「并行调研」 |
| **刻度自适应** | 缩放到 3 秒时刻度变 500ms 一格；缩到 24 秒时变 2s 一格 |
| **播放头永远在最上层** | 它是「现在」，别的都是「过去」 |

## 六、视觉语言：「记录纸」

| | |
|---|---|
| 底 | `#eef1f3`（冷调图纸灰白） |
| 网格 | `#dfe5e9` —— 横线用行分隔，竖线用刻度，**不用渐变伪造网格** |
| 墨 | `#16232e`（近黑的冷墨） |
| **朱红** | `#c4472c` —— 全片唯一彩色，只给播放头、失败、锁定态 |

顶栏有一个 **图纸 / 深色** 开关，切到深色就变成蓝图（`#0d1720` 底 + 青白线）。

| | 001 The Bench | 002 One Line | 003 Terminal | **004 Chronicle** |

## 八、实现要点

| 关注点 | 做法 |
|---|---|
| 平滑 | 几何（`transform` / `width`）**每帧直接写 DOM**，不经过 React |
| React 只负责离散态 | 活动泳道 / 段落、悬停、选中、缩放态、是否实时 —— 全程约 25 次重渲染 |
| 元素缓存 | 每次渲染后重建 `data-bar` 元素缓存，把 `from/to/gap` 从 dataset 里读出来 |
| 刻度池 | 固定 16 个刻度元素，按视窗算位置和文案，用不到的就 `opacity:0` |
| 滚轮 | 必须用 `{ passive: false }` 的原生监听，React 的 `onWheel` 拦不住默认行为 |

### 已知取舍

- **概览缩略图不能拖动**，只能点击跳转。拖视窗是下一次可以加的。
- **没有做子步骤的展开/折叠**。现在所有子步骤都画在同一根泳道条里，靠 2px 的缝分开。
- **移动端只做了「不崩」**（去掉外框、窄栏）。
